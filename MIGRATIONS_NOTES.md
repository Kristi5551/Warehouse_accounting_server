# Миграции и начальные данные (Flyway)

## Легаси: `V8__insert_initial_data.sql`

- **Не редактировать** после того, как миграция применена на **любом** окружении: Flyway сверяет checksum; изменение файла сломает `validate` / деплой. Доработки «в том же V8» **не допускаются** — только новые файлы `V{N}__…`.
- Рассчитана на **последовательное применение на пустой схеме** после V1–V7: в ней используются **жёстко заданные числовые id** (категории, товары, строки `stock_balances` и т.д.). На БД с иным порядком вставок или уже занятыми id возможны **конфликты или неверные связи** — это известное ограничение **легаси-сидов** для «чистой» установки.
- **V9** переименовывает склад по умолчанию; **V10** добавляет ограничение `CHECK (quantity >= 0)` для `stock_balances`; **V11** нормализует количества в позициях операций. Эти миграции **не дублируют** бизнес-сид из V8, а развивают схему/данные дальше.

## Что добавлять дальше

1. **Новые изменения схемы** — только новые файлы `V{N}__*.sql` (монотонно увеличивать `N`).
2. **Новые демо/сид-данные** — предпочтительно:
   - идемпотентные выражения: `INSERT … ON CONFLICT … DO NOTHING` / `WHERE NOT EXISTS`;
   - ссылки по **естественным ключам**: `email`, `article`, **имя** сущности (категория, склад), подзапросы `SELECT id FROM … WHERE …`, а **не** литералы вида `id = 1`, если можно избежать.
3. **Критические строки без Flyway** (админ, страховка склада «Основной склад» при отсутствии) — только в **`InitialDataSeed.kt`**, уже по естественным ключам (email, имя склада).

## Связка с Kotlin

- **`InitialDataSeed`** **не должен** повторять категории/товары/остатки из V8 при нормальном прогоне: он дополняет учётку администратора и при необходимости создаёт склад «Основной склад», если его ещё нет.
- Если нужен переносимый сид без привязки к id из V8 — добавляйте **новую** идемпотентную миграцию по правилам выше или расширяйте `InitialDataSeed` / отдельный сервис с теми же принципами.
